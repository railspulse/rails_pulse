# Aggregates come from all traffic; detail rows only from the requests worth inspecting

_Recorded 2026-10, before 1.0._

With `config.store_full_details = { above: :slow }`, a request is persisted as a `Request` row with its full `Operation` timeline only when it is at or above `request_thresholds[:slow]`, ran a query at or above `query_thresholds[:slow]`, errored (status 500+), or picked by `sample_rate` (1% by default). `above:` names a key from the host's own threshold hashes rather than a duration, because threshold keys are host-defined and capture has no numbers of its own: keeping detail for exactly a level the dashboard flags means every request or query flagged at that level has requests to open, and keeps p95 and p99 among the exactly-kept requests for most apps. The cost is that the thresholds set storage as well as dashboard colours; to store less, a host raises them or names a higher level. The sample stays an option because without it a route or query that never reaches the threshold has no request to inspect. The default, `:all`, stores every request. Every other request is folded — on the same single writer thread that already persists everything — into an in-memory accumulator, one bucket per route per hour and one per query per hour, which is flushed about once a minute into `rails_pulse_rollups`: counts, status counts, exact duration sums, min, max and a log-bucketed histogram (`RailsPulse::DurationHistogram`). When `SummaryService` builds an hour it merges raw rows with that hour's rollups, so counts, error rates, averages, minima, maxima and standard deviations stay exact, and percentiles stay exact wherever they land among the exactly-kept slow requests — which p95 and p99 do whenever the named request threshold sits below them. Only percentiles that land inside the rolled-up fast traffic are approximate, within the histogram's ~5% bucket width. With `store_full_details = :all` (the default), nothing changes: no rollups are written and the summary path is untouched.

The alternative actually requested (issue #349, an installation writing 28M operation rows a day) was a plain persistence threshold: only store requests and operations past a duration cutoff. It was rejected because every summary is computed from raw rows, so a bare threshold silently turns every dashboard number into a statement about the slowest few percent — request counts and requests-per-minute collapse, error rates divide by the wrong denominator, and p50 becomes the median of the slow tail. A monitoring tool whose headline numbers are artifacts of a config option is worse than one that stores less detail. Head sampling (deciding before the request runs) was also rejected: the decision must come after the response to guarantee that every slow or errored request is kept, which is the whole point of looking at one.

Rollup rows are written with a replace-upsert, not arithmetic in SQL: each writer incarnation (`host:pid:uuid`) upserts its own cumulative totals for the open hour under a unique key that includes the writer id, and the summary builder sums across writer rows in Ruby. That keeps the write portable across SQLite, PostgreSQL and MySQL and makes a repeated flush idempotent. The invariant that makes replacement exact is that an in-memory bucket, once discarded, never writes again under the same writer id: when a bucket's hour has long ended, or the bucket table grows past its cap, the accumulator flushes, clears everything and takes a new incarnation id, so later counts accumulate under a new key instead of overwriting the old row. SQL operations of non-captured requests still travel to the writer (slimmed to type, statement and duration) so query rollups keep the Queries page exact; template, cache and HTTP operations are dropped at the middleware because only the per-request timeline reads them.

The cost is honesty bookkeeping everywhere raw rows are read directly: the requests index and the route page's request table list only captured requests (they say so when the feature is on), the API's raw-window counts carry a `sampled_detail` flag, and job runs are untouched by the feature — they are low-volume and persist outside the writer. Backfilled or re-run hourly summaries read rollups as well as raw rows, so rollups are retained as long as raw requests (`full_retention_period`).
