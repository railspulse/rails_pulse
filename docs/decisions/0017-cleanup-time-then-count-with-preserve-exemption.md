# Cleanup deletes by age first, then by row count, and `preserve` is the only exemption

`CleanupService` runs from `CleanupJob` or `rake rails_pulse:cleanup`. It first deletes rows older than `full_retention_period` (operations, then requests, then queries and routes that no longer have children, then job runs and jobs, then exception occurrences). It then enforces `max_table_records` per table, deleting the oldest rows until each table is under its cap. Orphan checks use correlated `NOT EXISTS` so large tables do not time out. An `ExceptionGroup` with `preserve` set is exempt from every stage, including deletion of its occurrences, so a kept group keeps its backtraces.

Two alternatives were rejected. Age-only retention leaves table size unbounded on a busy app, and the whole point of storing data in the host's database (0006) is that the gem must protect that database from itself. Count-only retention deletes recent data on a busy day and keeps stale data on a quiet one, which makes the dashboard's time range lie.

The order matters for foreign keys and for meaning: age-based runs first so count-based only ever trims what retention would keep, and summaries are never deleted by count because they are the long-term record. Preserved and ignored exception groups sit outside `max_table_records[:rails_pulse_exception_groups]`: the cap is enforced against the deletable groups only, so a host that preserves many groups keeps them without the cap trimming its other groups for no gain.

Every delete is issued in bounded batches: at most `BATCH_SIZE` (5,000) rows per statement, with each batch chosen inside the database and each statement committed on its own. Tables whose children must go first (requests and job runs before their operations, exception groups before their occurrences) are walked `PARENT_BATCH_SIZE` (1,000) parents at a time. The cost of a run therefore grows with the number of statements, not the size of any one of them, so a table that has outgrown its cap many times over is trimmed without a statement, lock or transaction that scales with the overage. Collecting the ids in Ruby and deleting them with one `IN` list was rejected because the database's memory for parsing and planning that statement grows with the list, about 0.9 MB per 1,000 ids on PostgreSQL, which is enough to exhaust a small host. A per-run row budget was rejected as unnecessary: batches remove hundreds of thousands of rows in seconds, and a budget would leave a table over its cap for several runs. The batch sizes are constants, not configuration, because memory stays flat across the sizes that are reasonable.

Each table is a separate stage. A stage that raises is logged and the remaining stages still run; the first error is raised once all have finished, so the job is still reported as failed. This is safe because no stage relies on an earlier one: a stage either deletes its own child rows first or only deletes rows that have none.
