# Dashboard metrics come from summaries that `SummaryJob` precomputes, not from raw rows at read time

`RailsPulse::SummaryJob` runs hourly and writes one `Summary` row per subject and period type (hour, then day, week and month at their boundaries) through `SummaryService`, which upserts all rows for a period in bulk. Charts, metric cards and the health bar read summaries only. Raw requests and operations are kept for drill-down and are deleted by retention long before summaries are.

Computing percentiles from raw rows at read time was rejected. P95 over a week of requests for every route on one page is a sort of millions of rows per load, on the host's own database (see 0006), and it gets slower as the app gets busier, which is exactly when someone opens the dashboard.

Three consequences are deliberate. Data is up to an hour stale, and the dashboard says so with a banner when the job has not run (`warn_on_stale_summaries`). The overall request rollup (type `RailsPulse::Request`, id 0) is written even for an empty hour so its timestamp is a heartbeat that the banner, `rails_pulse:status`, storage pressure and cleanup all read. Hourly rows are pruned after `hourly_summary_retention` (two days) because only the one-day view reads them; the trade is precision of change-point detection against table size. `rake rails_pulse:backfill_summaries` rebuilds hourly summaries from whatever raw rows still exist.

Only hourly summaries are computed from raw rows, so the job's memory is bounded by one hour of traffic rather than growing with the period and with raised `max_table_records` caps. A day is rolled up from its hours, and a week or month from its days, by one `GROUP BY` over the child summaries that returns one row per subject; it uses only `SUM`, `MIN`, `MAX` and arithmetic because SQLite has no `STDDEV`. Count, total, average, min, max, status buckets and standard deviation combine exactly; P50, P95 and P99 are the count-weighted average of the children's, the same weighting `Tables::Base` applies when a chart range spans several periods, so stored long-period percentiles are estimates rather than exact. Exact long-period percentiles were rejected because they need every raw row of the period, which retention has usually deleted by the time a month closes and which is what made a month's summary cost hundreds of megabytes. A rollup first summarizes any child period missing its heartbeat row, so a gap in `SummaryJob` runs or a backfill of longer periods alone still produces complete totals. A period is summarized only once it has ended: its heartbeat row is what cleanup and the rollups trust to mean "fully aggregated", so a mid-period run (a backfill reaching today) writes nothing rather than a partial row that could be mistaken for final.
